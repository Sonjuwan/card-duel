# 프로젝트 설계

## 목표

2014년 초기 하스스톤의 전투 시스템을 참고하는 독립적 친구용 1:1 카드게임. 9개 직업, 영웅 능력, 영웅 체력 30, 덱 30장, 같은 카드 최대 2장, 마나 10, 전장 7개, 기본/일반/희귀 등급만 허용. 이후 확장팩 및 영웅급/전설급, 수집/랭크/과금, 일러스트와 사운드 제외. 원작 소스와 리소스를 추출하지 않는다. 카드는 독립적인 데이터로 관리하고 정식 배포 전에는 이름·문구·세계관도 독자적인 표현으로 정리한다.

## 폴더 구조

```text

    server/       Node.js + Socket.IO, 룸 서비스, 카드 저장소
    admin/        별도 로컬 밸런스 편집기

    engine/

  data/cards/     버전별 카드 JSON 데이터
  docs/           개발 진행/설계 문서
  package.json
  package-lock.json

```

## 데이터 흐름 (구현됨)

전장 테마는 `apps/client/src/classic-table.css` 및 `table-decor.tsx`에 분리한다. `table-visuals.ts`의 순수 함수는 카드 손패 위치, 도감 페이지, 서버가 이미 허가한 연속 PlayerView의 시각적 변화만 계산한다. 게임 상태 변경 및 플레이 가능 여부 판정은 기존 엔진과 서버가 담당한다.

1. React 클라이언트가 `Action`을 요청한다.
2. Socket.IO 서버가 방, 인증된 플레이어, 현재 revision, 중복 행동을 검사한다. 클라이언트가 보내는 actor ID나 마나/체력 등은 신뢰하지 않는다.
3. `applyAction`이 권한, 턴, 마나, 대상, 승패 등 게임 규칙을 검증하고 새 `GameState`를 반환한다. 실패하면 이전 상태를 유지한다.
4. 서버는 각 플레이어에게 `getPlayerView(state, playerId)`의 결과를 개별 전송한다. 상대 손패/비밀 신원과 양쪽 덱 순서는 직렬화하지 않는다. 공개 전투 기록에는 카드가 공개된 행동만 포함한다.
5. UI는 수신한 상태를 표시한다. 판정은 서버가 담당한다.

## 엔진 사용법

- `createCatalog(json)`: 외부 카드 데이터 검사 및 동전 추가
- `validateDeck(deck, catalog)`: 덱 30장, 중복 2장, 직업/카드 검증
- `createGame(catalog, [deck0, deck1], {seed, firstPlayer?, runtime?})`: 덱 섞기, 초기 손패, 멀리건 상태 생성
- `applyAction(state, actor, action, runtime?)`: 입력 상태를 변경하지 않고 새 상태 반환; 무효 행동은 `RuleError`
- `getPlayerView(state, viewer)`: 인증된 플레이어별 공개 정보와 본인 손패만 추출

`GameState`는 비공개 권위 상태다. `rng`, `catalog`, 카드 순서와 전체 손패를 포함한다. 카탈로그는 경기 생성 시 복제되므로 이후 데이터 수정이 진행 중인 경기의 밸런스에 영향을 주지 않는다. `revision`은 승인된 행동마다 1 증가한다. 테스트/시범 경기에서는 재현 가능한 시드 PRNG를 사용하고 실제 서버는 `node:crypto` 난수와 UUID로 셔플·랜덤 효과·카드 인스턴스 ID를 생성한다. 서버 동기 처리와 revision 검증으로 중복/오래된 행동을 차단한다.

## 모듈 역할

- `engine.ts`: 상태 전환, 턴, 전투, 소환, 비밀, 사망/이벤트 큐, 입력 검증.
- `effects.ts`: 허용된 선언형 효과와 대상 검증/처리. 카드 데이터에서 임의 코드를 실행하지 않는다.
- `auras.ts`: 지속 강화 재계산; 영구 강화와 지속 강화를 구분한다.
- `costs.ts`: 현재 장착 무기 및 전장의 비용 효과를 계산한다. 화면·서버·시뮬레이션에서 동일한 함수 사용.
- `playability.ts`: 공개 정보 기반으로 공격·대상·주문·영웅 능력의 사전 조건과 UI 사용 불가 사유를 계산한다. 서버의 최종 검증을 대체하지 않는다.
- `client/src/Battle.tsx`: 두 영웅, 양쪽 전장, 손패, 자원, 턴 종료, 멀리건 및 선택창을 표시하고 클릭/드래그를 처리한다. 권위 상태를 직접 수정하지 않는다.
- `client/src/battle-actions.ts`: 공개 뷰에 대한 순수 행동 계획 및 클릭/드래그 대상 검증. 기존 엔진의 공통 판정 함수를 이용하고, 입력 revision이 바뀌면 오래된 드래그는 폐기한다.
- `client/src/battle-pieces.tsx`, `battle.css`: 카드와 영웅의 재사용 가능한 표시 구성 요소, 독자적인 SVG 문장, 마나/능력치 색상, 반응형 레이아웃.
- `client/src/Lobby.tsx`: 직업 선택 및 AI/친구 모드를 분리하여 덱 편집기와 연결한다. `App.tsx`는 서버 연결, 덱 저장 및 화면 이동을 담당한다.
- `client/src/local-art-model.ts`, `local-art.tsx`, `local-cards.css`: 카드 ID로 결정하는 자체 SVG 일러스트와 클래스별 프레임. 외부 API/이미지 다운로드 없음. `card-names.ts`는 표시명만 전환한다. 카드 판정 및 실행은 엔진에 그대로 남는다.
- `hero-powers.ts`: 9개 직업 능력과 직업 전용 토큰.
- `decks.ts`/`simulate.ts`: 덱 생성 및 실제 엔진을 사용하는 시범 대전.
- `practice-decks.ts`: 사람용 9개 직업별 입문 추천 덱 및 기존 카드 유지 자동 채움. 이전 AI용 `starterDeck`과 별개다.
- `bot.ts`: 공개 전장, 본인 손패/비밀, 양쪽 공개 자원만으로 가상 상태를 구성한다. 실제 엔진으로 가능한 행동을 평가하여 즉시 승리, 유리한 교환, 카드 사용, 영웅 능력 등을 선택한다. 숨겨진 상대 손패/비밀, 덱 순서, 실제 서버 RNG는 받지 않는다. 무작위 효과는 독립적인 가상 난수를 사용하며 결과를 실제로 예측하지 않는다.
- `rooms.ts`: 방 코드, 플레이어별 재접속 토큰, 세션 연결, 권위 상태 저장. 방별 최대 2인, 서버 전체 방 최대 200개, 접속이 없는 방은 2시간 후 새 요청 시 정리한다.
- `room:action` 성공 응답은 해당 플레이어만 볼 수 있는 최신 방 상태를 반환한다. `room:sync`는 멤버에게 현재 상태를 조회시키고, 클라이언트는 같은 방의 오래된 revision 응답을 무시한다. 손패·비밀·선택 후보의 권한 분리는 동일하다.
- AI 방: 사람 1인 + 서버 AI 1인으로 시작. AI는 타이머로 한 번에 한 행동씩 실행하고, 모든 행동은 권위 엔진에서 재검증한다. 40행동 제한으로 턴 종료를 보장하며, 접속 중단 시 일시 정지하고 재접속 시 재개한다. AI 자리에 일반 플레이어가 참가할 수 없다.
- `card-store.ts`: 활성 카드 버전 관리. 새 JSON 작성 후 활성 포인터 변경, 오래된 버전 저장 요청 충돌 방지. 원래 파일은 보존하고 버전 간 비교는 읽기 전용이다.
- `catalog-snapshot.ts`: 경기 시작 시 카드 정의를 깊게 고정한다. 이후 행동에서는 정의를 재사용하고 동적 상태만 복사하여 기존 경기의 규칙이 바뀌지 않으며 처리 비용을 줄인다.
- `admin-server.ts`: 로컬 전용 카드 편집기. 127.0.0.1 바인딩, Host/Origin 확인, 크기 제한, JSON 검증. 게임 HTTP 서버에는 저장 API가 없다. 게임 서버는 시작 시 읽은 카탈로그를 사용한다.
- `config.ts` / `server.ts`: 기본 게임 서버는 127.0.0.1, LAN/VPN 모드는 명시한 사설 IPv4에 한정. 와일드카드/공인 주소 바인딩 거부. 브라우저 Origin 검증 및 HTTP 보안 헤더. 명시적 사설 HTTPS 프록시의 출처 1개를 지정할 수 있다.

## 현재 제한

- 카드 308종(기본 133, 일반 94, 희귀 81), 비수집 정의 24종. 직업 189종과 공용 119종의 대응표는 `ROSTER_PLAN.md`에 기록했다. 개발용 카드가 포함된 과거 스냅샷은 별도로 보존한다.
- 덱 위 카드 선택은 서버가 `pendingChoice`로 관리한다. 선택 완료 전 다른 행동을 거부하고, 선택 후보는 소유자의 `self.pendingChoice`에만 제공한다. 재접속 시 선택을 이어서 수행한다.
- AI 난이도 1~5: 1은 약한 무작위 선택 및 조기 턴 종료, 2는 유리한 후보 중 선택, 3은 기존 단일 행동 평가, 4는 공개 위협 평가와 인접 배치, 5는 상위 6개 후보별 두 번째 행동 평가. 서버에서 난이도를 검증해 방에 고정하고 재접속 시 동일하게 유지한다. 가상으로 뽑은 미확인 카드는 5단계의 후속 사용 후보에서 제외한다. 장기 전략, 상대 턴의 예측, 비밀 추론은 향후 개선 대상이다.
- 구현된 키워드/효과는 `EFFECTS.md` 참조. 사망/동시 발동/빙결/침묵/변신 등의 규칙은 이 독립 게임에서 정한 결정적 순서를 사용하고 원작의 모든 특수 사례와 일치한다고 주장하지 않는다.
- 일러스트/사운드/수집/랭크/과금 없음. 덱은 브라우저에 저장되고 방 상태는 서버 메모리에만 있다.
- 덱 초안은 카탈로그 해시별 브라우저 저장소로 보관한다. 새 밸런스에서 모든 카드가 유효한 기존 초안은 그대로 복원하되 이전 스냅샷은 수정하지 않는다. 최근 20번 되돌리기, 기존 카드 유지 자동 채움, 오류 확인용 공개 전투 기록 복사를 지원한다. 오류 기록에 방 코드·세션 토큰·미공개 카드 정보는 포함하지 않는다.
- 실제 브라우저 자동화는 개발 환경의 OS 소켓 권한 때문에 시작 단계에서 막혔다. Chrome/Edge에서 사용자 테스트가 필요하다.
- 서로 다른 인터넷망 연결을 위한 배포, TLS, 장기 운영 및 악성 트래픽 방어는 미완료. 클라이언트 서버 코드 및 localhost 네트워크 테스트는 구현했다. 직접 공개 포트 개방 금지 권장.

1. 환경/프로젝트 구조
2. 기본 턴제 엔진
3. 공통 효과 엔진: 현 활성 카드의 공통 효과 구현, 역사적 복합 판정 추가 검증 필요.
4. 9개 직업과 영웅 능력 구현 완료.

6. React 덱 편집기, 검색/필터/마나 분포, 저장 및 공유 코드, 이전 덱 복원, 기본 전장 UI 구현 완료(브라우저 직접 검증 미완료).
7. Socket.IO 방 코드 대전 서버 구현 및 두 실제 클라이언트 테스트. 인터넷 배포 미완료.
8. 로컬 관리자 밸런스 편집기/간편 효과 수치 편집/검증 전용 API/버전 보존/카탈로그 스냅샷 구현 및 API 테스트 완료.
9. 통합/보안/브라우저 테스트 계속 진행. 전투 엔진/서버/관리자 테스트와 전체 자동 경기 검증, 원격 배포 및 브라우저 테스트 남음.

## AI 연구 기반

`researchDeck`은 기존 카드 역할 분석과 엔진의 덱 검증을 사용한다. 어그로와 컨트롤은 기존 프로필을 활용하고, 미드레인지는 하수인 전개와 중반 마나 곡선, 빅덱은 고비용 하수인의 전투 능력과 생존에 별도 점수를 부여한다. 시드를 고정해 활성 카드 버전당 직업별 네 덱을 재생성한다. 기존 7개 스타일 상수는 기존 호출부에 그대로 제공한다.

상성 초기 가중치는 `apps/cli/research-models.ts`에서 공통 19개 계수에 자기 전략과 상대 전략별 계수를 적용하여 새 객체로 생성한다. 이 값은 이후 학습의 출발점으로 쓰일 가설이다. 두 번째 경기에서는 후보가 반대편 좌석의 자기 전략으로 플레이한다. 한 행의 쌍 점수는 두 방향을 포함한다. 소표본 결과는 초기값 진단에 사용한다.

연구 벤치마크에는 고정 덱을 전달한다. 기존 트레이너와 체크포인트는 기존 작업 필드를 계속 사용한다. 새 상성 학습을 연결할 때는 별도의 데이터 루트 및 버전별 스키마를 사용하고, 기존 공통 모델은 비교 대상으로 사용한다. 카드 버전에 따른 계승 검증은 이후 단계에서 추가한다.

상대 모델은 공개된 상대 직업과 최근 60개 공개 기록의 카드 ID를 해당 직업의 네 연구 덱과 비교한다. 비밀 및 동전 설치·사용에는 카드 ID를 기록하지 않는다. 카드가 어느 전략에서도 관찰될 수 있도록 빈도에 평활화를 적용하고, 로그 점수를 안정적으로 정규화한 뒤 균등분포를 10% 섞는다. 이 확률로 자기 전략의 네 상성 가중치를 선형 결합한다. 실제 덱의 분류는 벤치마크가 마지막 추론을 채점할 때 사용한다. 생성 카드, 표준 덱과 다른 덱, 상대 행동 패턴, 초기 예측 보정은 추가 검증이 필요하다.

### 연구 풀과 계정 진행의 경계

기존 `train-ai.ts`, 연구 벤치마크, 밸런스 대전과 통합 카드 평가기는 계정이나 성장 자료를 인자로 받지 않는다. 게임의 활성 카드 카탈로그와 엔진의 `deckCards`/`validateDeck`가 수집 가능 여부, 직업 및 복제 한도를 결정한다. 현 버전은 별도 로테이션 형식 정의 없이 카탈로그 선택으로 사용 범위를 정한다. 확장팩·퇴출 규칙을 추가할 때 연구 풀에도 같은 엔진 판정을 적용한다. `growth-store.ts`와 보유 카드 게임 모드는 별도의 게임 경로에 속한다. 저장소에서 활성 해금 단계별 AI 작업, 연구 UI 및 단계별 정규화 보고서 입력을 찾지 못했다. 외부 사용자 레거시 자료의 존재 여부는 확인하지 않았으며 연구기의 입력으로 포함하지 않는다.

### 전략 추론과 정규화

기존 공개 이력 항목에 추가한 선택 필드는 공개 플레이의 지불 마나·공개 대상 분류·선택지, 전투의 공격 대상 및 선택 가능 여부, 영웅 능력 마나를 담는다. 비밀 설치와 동전에는 식별자 및 증거 필드가 없다. 공격자가 영웅과 하수인 양쪽을 실제로 고를 수 있었고 공격이 비밀 등으로 우회되지 않았을 때만 선호 증거로 쓴다. 주문 효과 기반 증거는 공개 카드 정의와 선택한 대상을 활용하므로 모든 연쇄 효과의 실제 피해·회복량을 의미하지 않는다. 과거 기록의 증거 누락은 허용한다. 분류용 시나리오의 실제 덱 라벨은 채점에서 사용한다.

`apps/cli/card-value-trials.ts`는 원본 후보 덱, 같은 엔진에서 합법인 대체 카드와 평가 카드가 들어간 덱, 상대 덱을 구성한다. 한 묶음은 대체 카드·평가 카드를 각각 양쪽 좌석에서 실행한 네 경기다. AI 정책·탐색 예산·시드·기준 덱과 상대 덱을 고정한다. 직업 카드는 4×4 전략, 공용 카드는 9직업×4전략을 동일 비중으로 평가하며 상대 전략을 순환한다. 종류·비용·카드 역할로 대체 카드를 선택한다. 사용 빈도는 설명용으로 기록하며 점수는 묶음별 승점률 차이에서 산출한다.

`paired-substitution-basic-mean-v1`의 원시 단위는 [-1, 1] 범위의 승점률 차이다. 현재 점수는 `100 + 100 × (카드 원시 차이 − 합법 기본 카드 전체 평균 원시 차이)`다. 1점은 원시 승점률 차이 1%p에 해당하며 0점 아래도 허용한다. 기본 카드마다 동일한 1표를 부여한다. 현재 프로토콜에서 최소 16묶음 및 계획한 모든 조합의 완료를 요구한다. 구간이 넓은 점수 역시 추정치로 제공한다. 점수 구간은 추정한 기본 평균을 고정했다는 조건의 범위이며, 원시 95% 범위는 묶음 단위 보수적 추정이다. 순위 차이의 통계적 확정을 뜻하지 않는다.

카드 환경 해시, 기본 AI 가중치 지문, 시드·탐색·덱 생성 규칙의 프로토콜 지문과 카드별 구성을 기록한다. 고정 기준 JSON은 전체 기본 카드가 관측된 동일 평가 방식·모델·프로토콜로 제한한다. 카드별 구성 지문이 같을 때만 고정 기준 점수와 패치 차이를 계산한다. 서로 다른 엔진/평가 방식은 프로토콜 버전을 올려 격리한다. 운영 게임과 관리자 초안 참고 지표 및 과거 평가 문서는 각각 기존 의미를 유지한다.

평가 원시 묶음은 명시적 `--samples-dir`에 카드 단위로 저장할 수 있다. 방식·카탈로그·AI 가중치·덱과 시드 프로토콜이 같은 데이터만 읽으며, 임시 파일에서 원자적으로 교체한다. 일반 AI 학습 체크포인트와 서로 다른 형식과 루트를 사용한다.

### 정책 4의 공개 치명 반격

가중치에 따른 기존 예상 반격 점수는 위협을 제한된 크기로 잘랐다. 정책 4는 그 평가와 별도로 위협이 가능한 배치에서 **공개 자원으로 다음 턴 승리까지 도달하는 합법적 수순**을 게임 엔진으로 탐색한다. 도발, 질풍, 보호막, 빙결, 방어도, 무기와 영웅 능력이 적용된다. 추정 손패의 카드 사용은 탐색 후보에 넣지 않는다. 가상의 난수 변화나 제한 시간 만료로 끝나는 분기에는 치명타를 증명하지 않는다. 정책 4의 탐색은 후보 상태당 최대 24수, 한 결정을 통틀어 48~128회의 추가 엔진 전이를 허용한다. 후보 수순의 공개 치명타를 가중치 점수보다 우선하고, 이번 턴 안에 확인된 승리는 먼저 선택한다. 탐색 범위 안에서 수순을 찾지 못하면 위험이 미확인 상태다.

### 상성별 후보와 챔피언

16개 상성을 묶음 단위로 순환한다. 각 후보를 시작할 때 현 챔피언 가중치와 상대 행들을 동결한다. 후보는 현 챔피언에서 미세·중간·대규모 변이를 60/30/10 비율로 생성한다. 각 묶음에서 현 챔피언과 후보가 같은 덱·상대·난수에서 각각 선후공을 한 번씩 맡는다. 자기 전략 행의 가중치를 공개 이력 기반 상대 확률로 혼합하고, 후보 행은 해당 열 하나를 교체한다. 후보 승격이 진행 중인 다른 상성의 동결 표본을 바꾸지 않는다.

독립 시드의 32/128/512경기 단계를 적용한다. 중간·정밀은 각각 별도로 구성한 개발군·홀드아웃 덱을 쓴다. 경기 점수는 승 1, 무 0.5, 패 0이며 4경기에서 얻은 두 좌석의 후보-챔피언 차이를 묶음 단위로 집계한다. 4묶음마다 한 번 초기·과거 상대를 번갈아 검증한다. 최종 기준은 승점률 차이 +2%p 이상, 좌석별 및 초기·과거 상대 그룹에서 평균 비퇴화, 단측 정확 부호검정과 고정 전술 통과다. 동률 묶음은 부호검정의 유효 표본에서 제외한다. 유의수준은 전체 실험에서 `0.05 / (16 × (시도번호+1) × (시도번호+2))`(0부터 시작)다. 통계 결과는 현재 덱·프로토콜에 조건부다.

단일 작성자 락과 현재/이전 원자적 체크포인트에 카드 해시·프로토콜·시드·순환 위치·16개 챔피언·누적 경기·진행 후보·묶음 결과를 보관한다. 중단 지점은 완료한 묶음이며 저장된 시드에서 다음 묶음을 재생성한다. 연구 승격과 운영 게임의 챔피언 파일은 서로 다른 입력 경로를 사용한다.

### 통합 배포 전 검증

검증 대상은 체크포인트의 16개 현 챔피언을 복제한 행렬이다. 진행 중인 후보를 포함하지 않는다. 통합 플레이어는 자기 전략의 네 모델을 공개 추론 확률로 혼합하는 정책 4를 사용한다. 기준과 상대는 같은 카드 카탈로그의 배포 챔피언과 정책 2를 사용한다. 난이도 25와 96 탐색 노드의 통제된 대전을 같은 덱·시드·좌석에서 비교한다.

배포 검증은 학습 시드 공간과 겹치지 않는 예약 시드를 사용한다. 검증 덱은 중간·정밀 학습 검증 덱의 예약 슬롯을 제외한 별도 슬롯을 사용한다. 각 상성에 9묶음을 배정하고 직업을 순환한다. 네 전략 행의 고정 전술, 144개 전체 묶음, 중단 경기 0, 전체 승점률 개선 +2%p 및 단측 부호검정 p≤.05, 전략별 하락 −2%p 한도를 모두 확인한다. 16개 상성의 개별 퇴화 검정에는 .05/16을 적용한다. 검증 명령의 결과는 배포 심사의 자료이며 운영용 AI 설정 적용은 이후 배포 절차의 권한을 따른다.

검증 보고서는 완료 묶음마다 원자적으로 기록된다. 재개 시 카드·모델·비교 상대·시드·평가 버전이 모두 일치해야 한다. 동일 좌석의 대조·후보 경기끼리는 정확히 동일한 결정 입력을 재사용하며, 캐시는 묶음에서 두 경기가 끝나면 폐기한다. 엔진의 가상 상대 연습 덱 캐시는 불변 카탈로그별로 제한한다. 가상 엔진 상태는 이전 전투 기록을 복제하지 않는다.

### 통합 AI 실패 분석과 확인 후보

재현 도구는 동결된 기준 행렬과 원래 보고서의 지문을 대조한다. 같은 덱·시드·먼저 플레이하는 좌석·상대 정책을 유지한다. 정책 2에서 3을 비교하면 반격 샘플링 정렬 변화, 3에서 4를 비교하면 공개 치명타 탐색 변화, 정책 4 내부에서 배포 고정·균등 상성·공개 추론 상성을 비교하면 가중치와 추론 민감도를 구분할 수 있다. 보고서에 기록한 두 좌석 점수와 재현 점수가 다르면 중단한다.

정책 5의 실험 실행 옵션은 정책 2와 같은 반격 샘플링 및 정책 4와 같은 공개 치명타 탐색을 사용한다. 확인 후보는 손실이 난 두 자기 전략에 이 탐색과 배포 가중치를 적용한다. 다른 전략 행은 기존 통합 정책으로 평가한다. 검증 덱과 시드 범위는 최초 배포 전 평가와 분리했다. 카드 카탈로그, 가중치 지문, 후보 이름, 덱 분할 및 전략별 실행 정책을 보고서에 기록해 서로 다른 평가를 이어 쓰지 못하게 한다.

### 컨트롤 독립 실험

컨트롤에서만 배포 가중치와 상성 행 사이를 계수별로 보간하고 기존 공개 추론 확률로 혼합한다. 강도 0은 배포 가중치를 직접 사용하고 1은 기존 16상성 행을 사용한다. 개발·확인·후속 연구는 다른 예약 시드와 덱 슬롯을 배정한다. 개발 원시 묶음의 SHA-256과 해당 묶음에서 선택한 프로필을 확인 자료에 기록한다. 확인 판정은 기존 `evaluateIntegrated`를 호출한다. 원시 개발 및 확인 자료로 판정을 독립 재계산할 수 있다.

같은 고정 덱·좌석·선후공·시드에서 처음 달라진 행동을 찾고 그때까지의 동일한 상태를 확인한다. 두 정책에서 해당 행동 한 건을 교환하며 이후에는 각 정책에 다시 판단을 맡긴다. 해당 상태에서의 승점 영향만 확인하며 첫 행동의 효과를 다른 상황에 일반화하지 않는다.

도발 처리 실험은 남은 합법적 공격 후보의 피해를 조합하여 공격 자원을 아끼는 수순부터 검토한다. 비용 추정치는 분기 우선순위에 사용하며 치명타는 실제 엔진 전이로만 판정한다. 다른 실험은 전체 검사 예산에서 패스에 일부를 배정하고, 남은 예산을 최종 후보 최대 6개에 나눈다. 원래 기본 검사와 연구 옵션 모두 제한 시간, 후보 상태당 24회, 결정당 48~128회 엔진 전이 한도를 적용한다. 대전 재현 벤치마크는 AI가 사용하는 공개 관측으로 가상 상태를 구성하고 별도로 전수 탐색한다. 전수 탐색이 끝나지 않은 배치는 미확정으로 집계한다.

공개 증거 실험은 첫 결정에서 수집한 확률을 덱 라벨로 채점하고, 별도 대전에서 균등 상성 행·공개 추론·확신도 기반 혼합을 비교한다. 계수 분리 실험은 생존, 손패·탈진, 교환에서 선택된 계수만 교체하고 다른 계수는 고정한다. 실험용 옵션은 연구 작업이 명시적으로 요청할 때만 활성화된다.
