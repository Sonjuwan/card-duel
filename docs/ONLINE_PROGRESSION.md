# 계정·성장·온라인 대전 개발 계획 — 2026-11-22

## 결정 사항

- 기존 무료 오프라인/친구 대전과 카드 밸런스는 유지한다. 유저 계정과 개발자 권한은 서버에서 분리하고, 계정 없는 연습은 XP에 반영하지 않는다.
- 무료 시작 구성을 Render(Node 서버) + Supabase(Auth/Postgres) + Git 저장소로 계획한다. 실제 프로젝트 생성, 계정/서비스 키 및 배포는 별도 연결과 검증이 필요하다. 무료 한도 및 정책은 변동될 수 있다.
- PC와 모바일은 동일 웹 주소와 계정으로 연결한다. 서버 계정 데이터가 기준이며 기기 로컬 데이터와 자동으로 합치지 않는다.
- 랭크는 브론즈 5→1, 실버 5→1, 골드 5→1, 플래티넘 5→1, 다이아몬드 5→1 총 25단계. AI 덱 파워/판단 난이도는 각각 1~25로 별도 설정한다.
- 카드 전력 분류는 1~25, 희귀도와 별개로 관리한다. 전력/XP/승급 수치는 초기 임시 설정으로 제공하고 카드 수치 밸런스는 나중에 조정한다.
- 랭크가 높을수록 대전 XP가 많아지며, 9개 직업 순서대로 각각 10경기 플레이 퀘스트가 이어진다. XP로 카드가 순차 해금된다. 이후 보유 카드만 사용하는 계정 PvP로 확장한다.

## v0.91.0: 구현된 계정·성장·대전 기능

- 50% 승리를 가정한 144개 합성 경기 결과를 실제 SQLite에 기록하여 25랭크(18,860 XP), 카드 382장(122번째 결과에서 전부 해금), 퀘스트 14회 완료, 25랭크마다 실제 방 AI 설정과 덱 풀, 30경기마다 DB 재시작 및 두 로그인 세션 일치, 과거 원장 재전송 무중복, 덱 저장 보존, XP 문턱 인상/원복 시 보유 카드 유지 확인. 실전 승률이나 클라우드 부하를 의미하지 않는다.

- Supabase SQL 005~006으로 읽기 전용 스키마 준비 함수를 설치한다. 공개 배포 시작과 `verify:deployment -- --cloud`는 5개 테이블의 서버 접근/공개 키 차단, 정산 함수의 서버 실행 및 공개 금지, 실제 `service_role` 역할과 쓰기·RLS 우회 권한, RLS 및 anon/authenticated의 테이블/열/준비 함수 접근 금지를 확인한다. 실제 유저 데이터를 읽거나 보상 쓰기를 실행하지 않는다. 스키마 6 미만 또는 검사 실패 시 시작을 중단한다. 실제 PostgreSQL 수행은 클라우드 연결 후 검증한다.

- 로컬 및 클라우드 계정 저장소·클라이언트·기록 다운로드에 동일한 프로필 검증을 사용한다. 초기 v0.46 저장본의 누락 랭크 승수는 0으로 호환하고 별도 저장소 revision을 우선한다. 잘못된 XP·통계·중복 덱·카드/전적 형식은 기존 데이터를 덮어쓰지 않고 거절하며 과거 카드/직업 ID는 보존한다. 손상된 프로필도 세션 소유자 대조를 거쳐 로그아웃할 수 있다.

- 운영 승인 도구가 현재 앱과 동일한 계정/성장/활성 경기/개발자 응답 검증을 사용한다. 읽기 전용 계정 시험은 잘못된 대상의 기록 조회를 거절하고, 폐기 가능 계정 2개를 쓰는 승인 시험은 타계정 덱 저장 및 소켓 대전 진입 거절까지 검사한다. 성공 시 `identityBound: true`, 기존 시험 기록/세션 범위는 동일하다.

- 서버 재시작 및 기기 이어하기에서 성기사/주술사 영웅 능력의 생성 하수인 정의까지 신규 게임과 동일하게 복원한다. 호환되는 저장 경기의 방 모드, 참가 계정, 보상 식별자, 카드 영역 및 전투 상태를 검사하고 비정상 데이터는 일부 정산/복원하지 않고 시작을 중단한다. 호환 불가/만료 정책과 미정산 결과 보존은 유지한다.

- 인증 요청 제한 응답에 재시도 대기 시간(Retry-After)을 표시한다. 비밀번호 변경·복구 중 세션 폐기 결과가 불확실하거나 이후 공급자 변경 실패 시에도 기존 연결의 인증 캐시를 폐기하며, 변경 전 시작한 비동기 세션 조회가 뒤늦게 성공하지 않게 한다. 요청은 자동 재시도하지 않는다.

- 동일 브라우저의 다른 탭에서 계정이 바뀌었을 때 이전 화면의 보호된 HTTP 요청과 계정 대전 진입 요청은 표시된 계정 ID와 서버 인증 계정을 대조한다. 불일치는 저장·다운로드·계정 변동·방 생성 없이 거절하고 새 계정 조회/재연결을 유도한다. 계정 ID 자체는 인증 수단이 아니다.

- 성장 응답의 전체 랭크·XP·직업 순서와 개발자 운영 응답을 확인한다. 재접속/패치/계정 전환 이후 이전 성장 응답을 이용한 신규 대전이나 오래된 개발자 배포 준비 표시를 막는다.

- 새 조회가 진행 중이거나 상태 확인에 실패하면 계정 대전 시작 및 이어하기를 제한한다. 계정 정보와 활성 방의 응답 형식을 확인하며 최신 계정과 정확히 연결된 활성 경기만 이어갈 수 있다. 계정과 성장 패널 오류는 기존 진행에 영향을 주지 않는다.

- 재시작 복원 중 유효한 방 수가 서버 한도를 넘거나 중복 활성 계정/방/정산 키 및 잘못된 결과가 확인되면 시작을 중단한다. 운영자는 원인을 조사하고 백업을 유지하며 임의 삭제하지 않는다. 기존 만료/카드 호환성 정책은 유지한다.

- 개발자 /growth 및 verify:deployment에서 4시드·9직업·25랭크의 900개 생성 덱을 검사한다. 임시 카드 전력 합과 동일 시드/직업 인접 비교, AI 지능의 휴리스틱 또는 검색 설정을 표시한다. 기본 864개 인접 비교 전부 증가. 직접 설정된 전력/지능 역전 및 동일은 경고하며 자동 변경하지 않는다. 실제 승률·밸런스는 별도 검증이다.

- 클라우드 저장 경기 조회는 기본 키 페이지를 끝까지 모두 복원하며 불일치 시 부분 상태로 서버를 시작하지 않는다. 이메일 인증 전 가입은 [Supabase Auth의 실제 가입 응답 구현](https://github.com/supabase/auth/blob/master/internal/api/signup.go)의 사용자 객체와 토큰 응답 형식을 구분한다. 저장소 형식 오류는 세션 없음과 구분한다. 실제 외부 서비스 시험은 필요하다.

- 첫 카드 요청은 25초 제한과 재시도, HTTPS에서는 응답 본문 해시도 검사한다. 패치/롤백 시 버전과 카드 해시가 모두 맞을 때만 온라인 경기 시작·복원. 자동 새로고침이 한 번 실패하거나 탭 저장소가 없으면 계정 패널을 중지하고 수동 갱신을 안내한다. 기존 경기 티켓을 지우지 않는다.

- 운영 HTTPS의 WebSocket은 정확한 게임 서버 출처만 허용하고 HSTS, 동일 출처 자산 보호 및 폼 출처 제약을 적용한다. 로컬/LAN HTTP는 자체 출처 WebSocket을 계속 허용하며 HSTS는 적용하지 않는다. 로그인 제한은 정규화된 이메일 및 직접 연결 IP를 사용하고 임의 전달 헤더로 우회할 수 없다.

- 같은 Wi-Fi에서 `start-lan-test.cmd` 또는 `npm run build` 후 `npm run lan:test -- --list`, `npm run lan:test -- --host 실제사설IPv4`로 PC와 모바일의 같은 테스트 계정/경기 복원을 시험할 수 있다. 운영 DB/외부 키를 상속하지 않으며 `data/accounts/lan-test.sqlite`만 사용. 파일 삭제는 자동 실행하지 않는다. HTTP는 암호화되지 않으므로 가상 계정만 사용하고 공용 네트워크나 포트 포워딩은 금지한다.

- 이메일 확인이 필요한 클라우드 가입은 202 응답으로 구분하며 인증 전 세션 쿠키 및 진행 프로필을 만들지 않는다. 클라이언트는 확인 대기 상태와 로그인 안내를 표시하고 비밀번호 입력을 비운다. 실제 메일 전달은 외부 서비스 시험 필요.

- 기존 계정 대전에서 행동/동기화/저장/나가기 시 마지막 인증 후 60초가 경과한 경우 계정 세션 및 개발자 권한을 재검증한다. 외부 폐기·만료·강등은 재확인 시 활성 좌석만 해제하고 진행 상태를 보존한다. 저장소 일시 장애는 행동을 거절하고 재시도할 수 있으며, 정상 로그아웃·비밀번호 변경은 즉시 연결 해제한다. 게스트는 영향 없다.

- 운영 엔트리 프로세스의 실제 3회 시작 및 종료, 독립 계정 로그인과 로컬 SQLite 파일의 덱/XP/저장 랭크 경기 복원, 조기 항복 무XP·점검 준비 확인 시험을 `npm run test:online-smoke`에 포함한다. 외부 서버 및 실제 모바일 시험은 별도다.

- 서버 버전/카드 해시 불일치를 감지해 일반 로비는 즉시 최신 빌드로 갱신하고 기기 AI 경기는 현재 작업 스레드 해제 및 로비 복귀까지 적용을 유예한다. 카드 변경 시 저장 경기 호환 제한 경고와 확인, 이전 버전에서 새 리매치는 차단. 이전 서버로 롤백되면 대기 안내를 취소한다.

- 점검 상태를 SQLite/Supabase에 보존해 재시작·클라우드 휴면 이후에도 유지한다. 점검 시작은 즉시 신규 계정 방을 차단하고, DB 저장이 완료되어야 패치 준비로 인정한다. 저장 실패는 차단 상태 유지·재시도 안내, 점검 종료도 저장 성공 이후에만 허용한다. SQL 004 마이그레이션 필요. 최초 운영 서버는 점검 상태로 시작하며 이후 DB 값이 우선한다.

- 실제 배포 후 URL의 버전/카드 해시/성장 해시, 게스트 API 차단, HTTPS 보안 쿠키 및 WebSocket을 확인하는 `online:smoke` CLI. 승인 대상 체크아웃의 카드·성장 설정 및 배포용 AI 모델과 해시·세대를 대조하며 동일 버전의 잘못된 배포도 거절한다. 기본은 공개 읽기 전용이며 `--account` 옵션은 기존 테스트 계정만 별도 두 세션으로 로그인·조회·로그아웃한다. [배포 승인 체크리스트](RELEASE_ACCEPTANCE.md)를 단계별로 진행한다.
- `online:smoke -- <HTTPS 출처> --ready`는 일반 계정을 거절하고 개발자의 점검 저장·활성 경기·미정산 보상·경기 저장 오류를 마지막으로 조회해 모두 안전해야 성공한다. 배포·DB·점검 상태를 변경하지 않으며 현재 운영 버전 체크아웃에서 실행한다.
- 계정 덱의 신규 저장·덮어쓰기·삭제는 지정된 이름 하나에만 적용한다(`PUT /api/account/deck`). 다른 이름의 덱 또는 XP 변경과 충돌하면 최신 계정 revision으로 안전하게 재시도하고, 같은 이름의 비교 대상이 달라졌다면 409로 거절해 기존 저장본과 편집 초안을 보호한다. 기존 전체 목록 PUT은 이전 클라이언트 호환을 위해 유지한다.
- `online:acceptance -- <HTTPS 출처> --disposable-test-accounts`는 운영자가 별도로 등록·인증한 신규 시험용 유저 두 명으로 실제 덱 저장/실시간 동기화, 랭크 AI 저장·다른 기기 이어하기, XP·퀘스트 및 보유 카드 PvP 양측 전적을 검증한다. 현재 버전의 승인 해시 및 기존 진행 기록 없음, 점검 종료를 사전 확인하며 시험 기록은 남는다. 일반 유저나 개발자 계정에 사용하지 않는다. 실제 공급업체와 물리 브라우저는 별도 검증한다.
- `test:online-smoke`의 격리된 실제 서버 프로세스 버전 교체 시험은 임시 카드/성장 설정 변경 및 롤백 후 기존 계정 덱·XP·랭크·퀘스트·전적과 새 해금 카드의 영구 보존, 새 기기 로그인을 확인한다. 실제 원본 카드/성장/학습 데이터는 변경하지 않는다.
- 모바일 계정 패널 접기/랭크·XP 요약 유지, 성장 및 저장 경기 조회 오류 재시도, 25개 전력 등급별 현재 보유/전체·다음 XP. 서버와 동일한 공식으로 정규 승/무/패 XP 및 10경기 퀘스트 추가 보상을 안내한다. 개발자 운영 상태는 연결된 화면을 펼쳐 조회하는 동안 자동 갱신하며, 오래된 상태나 실패·연결 단절에는 재확인을 요구한다.
- 점검 시작 시 새 서버 덱 저장/삭제 및 비밀번호 변경/복구 완료도 거절한다. 기존 요청은 끝까지 처리하며 `pendingDeckChanges`/`pendingCredentialChanges`가 모두 0이 되어야 `readyForPatch`가 참이다. 로그인·가입·로컬 편집·저장된 기존 경기와 정산은 유지한다. 이는 단일 운영 인스턴스와 점검을 유지하는 수동 배포 절차를 전제로 한다.
- 계정 HTTP 요청은 25초 제한, 동일 출처·캐시/리다이렉트 차단 및 화면 갱신 중 이전 조회 취소를 적용한다. 일시적 통신 실패는 로그인 세션 만료와 구분하며 최신 상태를 확인하지 못하면 새 대전 시작을 제한하고 재시도를 안내한다. 쓰기 응답 유실은 실패/성공으로 단정하지 않는다.

- 같은 계정 전용 활성 대전 조회 및 실시간 상태 알림. 진행/대기/연결 여부를 표시하고 저장 후에만 다른 기기의 로비에 반영한다. 방 코드, 토큰, 상대 계정 정보는 반환하지 않는다. 이미 진행 중이면 새 계정 대전 대신 이어하기를 제공한다.

- 원본 학습 폴더를 Git에서 제외한 구조를 유지하면서 호환 챔피언만 `data/ai-release`에 포함한다. 기존 43,912게임(7회 승격), 6,848게임(0회 승격) 모델을 각각의 카드 해시별로 보존했다. 로컬 챔피언 우선, 배포 스냅숏 대체, 일치 모델 부재 시 기본 가중치 순이며 다른 카드 버전의 모델을 강제로 적용하지 않는다.
- `npm run ai:release`(선택 `-- --all`)로 로컬 챔피언만 내보낸다. 학습 체크포인트/시도/잠금은 복사하지 않고 이전 배포보다 오래된 모델로 덮어쓰지 않는다. 개발자 상태와 배포 사전 검사에 선택 모델 출처와 학습 수를 표시한다. 모델의 실제 AI 강도 측정이나 추가 학습은 하지 않았다.

- 계정 화면에서 현재 직업 또는 퀘스트 직업의 성장 추천 덱을 생성한다. 실제로 소유한 카드 ID만 사용하고 같은 전력 단계의 미해금 카드까지 사용하지 않는다. 잠정 전력 합계는 실제 카드 밸런스와 별개다. 다음 해금 진행률과 이름/단계/소유 상태 필터도 표시한다.
- 로컬 성장 설정 도구에서 이전 백업을 현재 카드 버전의 검토용 초안으로 불러오고, 검사 후 명시적으로 저장할 수 있다. 되돌릴 때도 현재 설정을 새 백업으로 보존하고 충돌하거나 비호환인 파일은 적용하지 않는다.

- 개발자 계정은 점검 모드를 시작/종료할 수 있다. 서버가 새 계정 랭크 AI, 개발자 시험, PvP 방 생성·참가·매칭을 차단한다. 진행 경기·기기 복원·저장·정산·일반 연습은 계속 가능하다. 실시간 상태가 연결된 모든 기기로 전파된다.
- 개발자 운영 상태의 계정 패치 준비는 점검 모드가 켜져 있고 진행/대기 계정 방, 저장 대기/실패, 미정산 결과 모두 0인 경우에만 표시한다. 이는 서버의 현재 상태이지 외부 배포 성공 보장이 아니다.

- AI 작업을 경기 종료/이탈·서버 정지 시 취소하고 큐 대기 12초, 실행 6초 제한과 실패 재시도 간격을 적용한다. 실제 작업 스레드가 종료된 뒤 다음 작업을 시작한다. 개발자 계정에서 접속 수, 진행/대기/종료 방, AI 대기열, 메모리(RSS), 미정산 및 저장 실패 상태의 집계만 볼 수 있다.
- `npm run online:load -- 12 8`는 로컬 합성 계정 14개 소켓에서 9직업 AI 12경기(25단계 6경기)와 성기사·주술사 PvP 1경기를 실제 실행한다. 영웅 능력 73회, PvP 소환물과 양측 정산, 기대 계정 ID를 검사한다. 측정 예: 소켓 227건 p95 88ms, 최대 104ms / 계정 조회 104건 p95 7ms, 최대 102ms / 전체 5.92초 / 프로세스 RSS 332MiB(테스트 서버·클라이언트 포함). 실제 무료 호스팅 수용량 또는 AI 승률 측정이 아니다.

- 계정 화면에서 내 서버 진행 기록(JSON)을 다운로드한다. 자기 계정 인증으로만 조회하며 비밀번호, 이메일, 세션 토큰은 포함하지 않는다. 다운로드한 기록은 참고용이며 다시 서버에 업로드해 XP나 랭크를 바꾸는 기능은 없다.
- 로컬 SQLite 운영 백업 CLI는 실행 중인 DB를 일관된 사본으로 만들고 무결성 검사 후 새 파일로 발행한다. 백업 사본의 로그인 세션을 제거하므로 이전 로그인 토큰이 복원되지 않는다.

- 개발자 성장 화면에서 가상 승률 35/50/70%와 퀘스트 수행/미수행 조건의 판수 예측을 비교한다. 실제 경기의 승률 측정이 아니며 랭크/XP 지급 함수만 재사용한다. 기본 설정에서 퀘스트 수행 시 다이아몬드 1 도달 206/144/103판, 전체 카드 획득 150/122/100판. `npm run progression:simulate` (선택 `-- --no-quest --json`)으로 재현한다.
- 카드 패치 검증·저장·이전 버전 활성화 및 성장 설정 검사에서 실제 225개 랭크 AI 덱을 생성해 검증한다. 삭제되는 카드의 전력 오버라이드처럼 충돌하는 설정이 있으면 저장/활성화를 거절한다. 먼저 /growth에서 오버라이드를 해제하고 다시 패치를 검사한다. 서버 시작 때에도 덱 유효성을 점검한다.

- 대전 종료 후 계정 원장에 확정된 XP, 직업 퀘스트 완료·보너스, 새 해금 카드, 승급 랭크를 표시한다. 아직 정산되지 않은 경기는 지급 완료로 표시하지 않고 지연된 소켓 응답으로도 보상을 되돌리지 않는다. 기존 전적에는 없는 새 필드를 선택적으로 지원한다.
- 계정 화면에서 25개 랭크의 AI 덱·판단 단계, XP 진입 조건, 현재 위치와 9개 직업의 10경기 퀘스트 진행표를 볼 수 있다.

- `npm run web`으로 실행하면 기본적으로 `data/accounts/accounts.sqlite`에 로컬 계정과 덱을 저장한다. DB는 Git 및 배포 파일에 포함하지 않는다. 비밀번호는 scrypt, 앱 세션은 무작위 토큰의 SHA-256 해시로 저장한다.
- 등록한 이메일로 다른 기기에서 다시 로그인하고 덱을 불러온다. 동일 서버 계정의 여러 기기 세션은 독립적이다. 계정 인증 소켓에는 데이터가 포함되지 않은 변경 알림만 보내고, 각 기기가 인증된 최신 프로필을 자동 조회한다. 등록되지 않은 소켓이나 다른 계정은 해당 알림을 받지 못한다. 덱 저장은 revision 비교로 충돌을 감지하며, 20개까지 저장한다.
- 등록 계정은 기본 `player`이다. 개발자 역할은 서비스 운영자가 DB에서 명시적으로 부여할 때만 적용한다. 기존 카드 관리 프로그램은 별도의 로컬 관리 도구 그대로 유지한다.
- 개발자 계정은 25개 랭크 중 원하는 실제 AI 덱/지능 설정을 전체 카드 덱으로 시험할 수 있다. 서버에서 권한을 확인하고 다른 계정이나 일반 권한의 재접속을 거절한다. 시험 경기의 XP·전적·퀘스트·랭크는 변경되지 않는다.
- 서버 AI 판단은 단일 제한 작업 스레드에서 계산하며 서버 본체가 합법 행동과 상태 revision을 검증한다. 계산 중 다른 경기 연결을 처리하고 이미 종료 또는 변경된 경기의 응답을 버린다. 실제 무료 호스팅의 동시 접속 수는 별도 부하 시험이 필요하다.
- 패치로 불합법해진 기존 계정 덱은 원본을 보존한다. 사용 가능한 카드만 가져오는 복원용 초안을 만들거나 다른 합법 덱을 별도로 저장할 수 있으며 새 불합법 덱은 서버가 거절한다.
- 계정 덱 및 전체 카드 연습 모드를 보존한다. 랭크 AI와 계정 PvP 접속 시 보유 카드 검사를 서버에서 적용한다. 덱 편집 시 기본 보유 카드 필터를 제공한다. 클라이언트에서 XP, 랭크, 역할을 직접 바꾸는 API는 없다.
- LAN 테스트는 같은 네트워크의 사설 IPv4에 `CARD_DUEL_HOST`를 설정하고 해당 주소로 접속한다. LAN HTTP는 암호화되지 않으므로 테스트 전용 비밀번호만 이용한다. 실제 사용자 가입은 HTTPS 배포를 사용한다.

### 로컬 계정 DB 백업 및 복구

1. 비공개 백업 폴더를 만든다(예: Git에서 제외된 `data/accounts/backups`).
2. `npm run account:backup -- --output data/accounts/backups/accounts-2026-11-22.sqlite`. 파일 이름은 항상 새 이름을 사용한다. `CARD_DUEL_ACCOUNT_DB`를 지정한 서버라면 백업 실행 환경에서도 같은 경로를 사용한다.
3. `npm run account:backup -- --verify data/accounts/backups/accounts-2026-11-22.sqlite`로 무결성을 다시 검사한다. 백업은 개인정보와 비밀번호 해시 등을 포함하므로 다른 사용자에게 공유하거나 소스·Git에 넣지 않는다.
4. 복구가 필요한 경우에만 서버를 완전히 정지하고 현재 원본 DB와 WAL/SHM 파일이 있다면 함께 안전한 별도 폴더에 보존한 뒤, 검사된 백업을 원래 DB 경로에 복사한다. 해당 시점 이후 변경은 복구 파일에 없으므로 덮어쓰기 전 운영자가 확인한다. 서버를 재시작하고 계정으로 다시 로그인한다. 자동 복원 또는 DB 덮어쓰기 명령은 제공하지 않는다.
5. 이 도구는 SQLite 전용이다. Supabase 운영 데이터는 실제 프로젝트 연결 후 Auth와 PostgreSQL 양쪽의 정식 백업/복원 절차를 검증해야 한다.

### 후속 패치 운영 절차

1. 로컬 카드·성장 개발자 도구에서 초안을 검사하고 `npm run verify:deployment`를 실행한다. 카드/성장 버전 및 게임 버전을 확인한다.
2. 현재 서비스의 개발자 계정에서 점검 모드를 시작한다. 신규 계정 대전이 중단되지만 이미 진행 중인 게임을 강제로 종료하지 않는다. 대기 방은 참가할 수 없으므로 유저가 나가거나 만료를 기다린다. 저장 후 나간 랭크 AI도 진행 경기에 포함한다.
3. 상태 확인 버튼을 눌러 계정 패치 준비가 완료됐는지 확인한다. 활성 계정 방, 대기 방, 미정산, 저장 실패가 없어야 한다. 불완전한 저장이 남으면 배포하지 않는다. 필요하면 운영자가 현재 계정 DB를 백업한다.
4. 새 버전은 이전 인스턴스에서 DB에 성공적으로 저장한 점검 상태를 이어받는다. `CARD_DUEL_MAINTENANCE=1`은 최초 DB 초기화에만 적용되는 값이다. 한 인스턴스 전제이며, 이전 인스턴스가 정지하기 전까지 새 계정 대전을 열지 않는다. 카드 카탈로그가 바뀌는 패치에는 이전 진행 중 방 복원이 지원되지 않으므로 위 단계가 특히 중요하다. 일반 서버 연습도 재시작 시 종료될 수 있다.
5. 새 서버의 버전·성장 해시·계정 저장소·개발자 권한을 확인하고 테스트 계정으로 필요한 시험을 마친다. 이전 인스턴스가 더 이상 게임 요청을 처리하지 않는 것을 확인한 다음 개발자 모드에서 점검을 종료한다. 이 시스템에 자동 Git 푸시/배포 권한은 부여하지 않는다.

### 클라우드 연결 (설정 파일 준비, 미배포)

1. Supabase 프로젝트를 생성하고 SQL 편집기에서 `deploy/supabase/001_accounts.sql`, `deploy/supabase/002_ranked_matches.sql`, `deploy/supabase/003_account_rooms.sql`, `deploy/supabase/004_runtime_settings.sql`, `deploy/supabase/005_schema_readiness.sql`, `deploy/supabase/006_server_role_readiness.sql`을 순서대로 실행한다. 기존 001~005 운영 DB에는 빠진 번호만 순서대로 추가 적용한다(005~006은 계정/경기 행 변경 없음). Auth 이메일 가입 및 이메일 인증 설정을 확인한다. 이메일 확인을 활성화한 경우 가입 후 받은 이메일을 확인하고 다시 로그인한다.
2. Render 웹서비스에서 저장소를 연결한다. `render.yaml`의 무료 웹 서비스 설정을 참고한다. 자동 커밋 배포는 끄고 검증된 패치만 수동 배포(참고: [Render Blueprint 명세](https://render.com/docs/blueprint-spec)). 빌드 `npm ci && npm run typecheck && npm run build && npm run verify:deployment`, 시작 `npm run server`.
3. 아래 환경 변수를 Render의 비밀 환경 설정에 입력한다. 소스 코드나 클라이언트에 넣지 않는다.
   - `CARD_DUEL_ACCOUNT_BACKEND=supabase`
   - `CARD_DUEL_PUBLIC_DEPLOY=1`, `CARD_DUEL_HOST=0.0.0.0`
   - `CARD_DUEL_PUBLIC_ORIGIN=https://실제-서비스-주소` (경로 및 끝 슬래시 제외)
   - `SUPABASE_URL=https://프로젝트.supabase.co`
   - `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (서버 API 키)
4. Supabase Auth Site URL에 실제 HTTPS 서비스 주소 설정. 데이터베이스 연결 확인, PC·모바일 각 로그인 및 덱 동기화, 재배포 이후 덱 지속성, 개발자/유저 권한 검사. 기본 메일 서비스는 팀 멤버 주소, 프로젝트당 시간당 2통의 테스트용 제한이 있다(2026-11-22 확인, [공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)). 일반 등록 유저 이메일 인증에는 별도 SMTP 설정이 필요하다. 무료 제공 범위는 별도 확인하며 비용 발생 설정은 운영자 승인 없이 하지 않는다.
5. 비밀번호 복구는 기본 꺼짐(`CARD_DUEL_EMAIL_RECOVERY=0`). 실제 SMTP를 설정하고 Reset password 템플릿에 `{{ .Token }}` 인증 코드를 포함(예: `<p>Card Duel 복구 코드: {{ .Token }}</p>`), 테스트 주소에서 발송/인증/비밀번호 변경을 확인한 후에만 `CARD_DUEL_EMAIL_RECOVERY=1`로 바꾼다. 비밀번호를 아는 사용자는 로컬/클라우드에서 현재 비밀번호 검증 후 변경할 수 있다. 변경 시 기존 앱 로그인 세션은 모두 폐기되며 계정 진행 기록은 유지된다.
6. `npm run build` 후 `npm run verify:deployment`로 로컬 25×9 AI 덱과 성장 버전을 점검한다. 운영 환경 변수를 설정한 경우에만 `npm run verify:deployment -- --cloud`로 다섯 개 테이블의 서버 읽기 권한 및 공개 키 차단을 점검한다. 클라우드 서버 시작 시에도 이 검사를 실행하며 잘못된 설정으로 시작하지 않는다. 실제 계정 가입 및 대전 원장 RPC, 인증된 일반 사용자 권한은 별도 서비스에서 시험한다.

Supabase Auth로 비밀번호를 검증하고 서버가 자체 만료 및 폐기 가능한 세션을 발급한다. 세션과 게임 데이터는 Supabase DB에 저장하므로 Render의 휘발성 파일 시스템과 분리된다. 테이블은 RLS 활성화 및 일반 API 직접 접근 권한 제거로 서버만 변경한다. 인증 속도 제한 및 만료 세션 정리를 구현했다. 운영 전 실제 서비스 검증, 계정 폐기/개인정보 청소, 프록시 기반 속도 제한 검토가 필요하다.

### 현재 성장 정책 (임시 조정값)

- 브론즈 5(1단계)부터 다이아몬드 1(25단계)까지, 현재 랭크에서 3승 이상 및 다음 랭크 AI 전력에 해당하는 카드 해금 최소 XP를 만족하면 승리 시 승급한다. XP가 부족하면 승리 카운트는 유지된다. AI 덱 파워/지능은 각각 현재 랭크에 대응한다. `data/progression/online.json`의 `rankTuning`에서 각각 1~25 값으로 변경할 수 있다. 기존 계정은 다운그레이드하지 않는다.
- 신규 계정은 9직업 연습 기본 덱에 포함된 카드의 합집합(현재 90종)으로 시작한다. 나머지 292종은 임시 전력 2~25 분류에서 XP 순서로 해금된다. `cardPowerOverrides`에서 카드 ID별 전력을 지정한다. 현재 자동분류는 마나/전투 특성을 이용한 임시 순서이며 실제 강도·카드 밸런스 평가가 아니다. 초기 카드 전력은 1이다. AI는 높은 전력 단계에서 유사 마나/종류의 더 높은 전력 카드로 순차 교체하여 덱의 임시 전력 합계가 감소하지 않게 한다.
- 승리 XP = 20 + 랭크×10, 패배 50%, 무승부 70%. 해당 퀘스트 직업으로 인정 경기 10회 완료 시 100 + 랭크×10 추가. 9직업을 전사→주술사→도적→성기사→사냥꾼→드루이드→흑마법사→마법사→사제 순으로 순환한다. 6턴 미만 조기 항복은 XP/퀘스트 제외. 카드별 추가 해금 비용 기본값 8+전력×3 XP, 각각 누적해 순차 해금한다(`unlockXp`로 조정 가능). 이미 해금한 카드 소유는 패치로 회수하지 않는다. 로그인/프로필 조회로 새로 지급된 카드도 DB에 기록한다.
- 계정 소속 방만 서버 정산하며 계정 ID+UUID 경기 원장에 중복 XP/전적을 방지한다. 계정마다 동시에 한 경기만 진행한다. 계정 전용 PvP는 친구 코드 및 가까운 AI 랭크 우선 상대 찾기를 제공하며 보유 카드만 사용한다. PvP는 아직 비랭크이며 XP/랭크 보상은 없지만 양측의 승·패·무 전적이 기록된다. 각각 모드별 누적 전적과 최근 30경기를 계정에 보존한다. 이전 버전의 경기 기록을 임의로 꾸며내지 않는다.
- 다른 기기의 계정 로비에서 '다른 기기 대전 이어하기'를 선택하면 서버가 소유권을 확인하고 진행 방을 이전한다. 이전 연결은 제어권을 잃는다. 계정 대전은 권한이 제한된 DB에 승인 상태를 저장하고 성공 응답을 보낸다. 랭크 AI '저장 후 나가기' 및 서버 재시작 후에도 복구할 수 있다(랭크 AI 재접속 유효 시간 24시간, 모두 떠난 계정 PvP 30분, 한 PvP 상대가 남으면 기존 5분 승패 규칙). 카드 해시가 바뀌면 호환되지 않는 진행 방은 복원하지 않으나 저장된 미정산 결과는 원장으로 안전하게 재처리한다. 한 서비스 인스턴스 전제이며 복수 서버 간 동시 경기 처리는 아직 지원하지 않는다.
- 로컬 권한 부여: `npm run account:role -- 이메일 developer` (일반 복귀는 `player`). 클라우드에서는 Supabase SQL 관리자만 `duel_accounts.role`을 변경한다. 웹 개발자 상태 패널은 서버에서 역할을 확인한다. 카드 편집/배포 권한은 기존 로컬 관리 도구와 Git/호스팅 관리자에만 있다.
- `npm run balance` 후 `http://127.0.0.1:3001/growth`에서 전력/AI 지능/해금 XP 비용만 설정하고 모든 카드 해금 순서와 랭크 최소 XP를 검증할 수 있다. 카드 수치는 수정하지 않는다. 저장 전 검사, 카드 버전 및 설정 해시 일치 검사를 적용한다. 이전 설정은 `data/progression/history`에 보존하며 게임 재시작/배포 시 적용한다. 공개 게임 서버는 해당 편집 API를 제공하지 않는다.
- 소스 패치 시 `package.json` 버전을 올리고, 카드/성장 설정 및 DB 마이그레이션을 검증 후 배포한다. `/api/version`에서 게임 버전·카드 해시·성장 해시를 확인한다. 브라우저 진입/재연결 시 새 게임 또는 성장 설정을 불러온다. 활성 기기 AI 경기 중에는 자동 페이지 새로고침을 막는다. 로컬 연습 대전 전적은 계정 랭크 전적과 분리한다.

## 후속 단계 (실제 배포 전)

1. 실제 Supabase/Render 무료 프로젝트 연결, SQL 실행, HTTPS 및 키 설정, PC/갤럭시 S24 브라우저 실기 검증. 계정 생성 및 클라우드 배포는 아직 하지 않았다.
2. 운영 보안 강화: 실제 이메일 확인/복구 시험, 개인정보 삭제·백업, 대량 요청 방어, 사설 테스트 후 공개 서비스 결정.
3. PvP 별도 MMR(요구 시), 다중 서비스 인스턴스, 장애 복구 및 카드 패치 호환성 추가 검증.
4. 카드 밸런스는 사용자 지시에 따라 나중에 검토, 임시 전력/XP 분류를 검증된 덱 성능 및 플레이 테스트로 교체.
