# 실제 공개 시험 및 배포 승인 체크리스트

이 문서는 개발 후보를 실제 유저가 사용하는 서비스로 연결하기 위한 순서다. 기존 카드 수치와 AI 학습 원본은 바꾸지 않는다. 모든 공개 시험 전에는 가상의 테스트 계정을 사용하고, 일반 유저 등록은 실제 검증 후 시작한다.

## 1. 설치와 비용 승인

- 기존 저장소 또는 새 비공개 Git 저장소를 연결한다. 현재 소스에서 `npm ci`, `npm run typecheck`, `npm test`, `npm run test:online-smoke`, `npm run verify:deployment`를 실행한다.
- 사용자 본인의 Supabase/Render 프로젝트를 연결하고 `docs/ONLINE_PROGRESSION.md`의 환경 변수와 SQL 마이그레이션을 적용한다. 비밀번호 및 비밀 키는 제공업체의 비밀 설정에 입력한다. 채팅, Git, 화면 캡처, 로그에 공유하지 않는다.
- 실제 무료 요금제 조건 및 휴면/저장 한도를 제공업체에서 확인한다. 비용 발생, 유료 전환, 추가 인스턴스는 별도 운영자 승인 후 진행한다.
- Render 운영 환경에서 `npm run verify:deployment -- --cloud`를 실행한다. SQL 001~006 적용 후 스키마 버전 6 이상, 5개 테이블 서버 읽기, 실제 `service_role`의 쓰기와 RLS 우회 권한, 정산 함수, 공개 키·anon/authenticated 접근 차단 및 RLS를 데이터 변경 없이 확인한다. 실제 계정 가입과 대전 원장 쓰기는 아래 시험에서 따로 확인한다. 이 단계가 실패하면 공개 대전을 시작하지 않는다.
- 운영 서버는 단일 인스턴스로 시작하며 처음에는 `CARD_DUEL_MAINTENANCE=1`로 저장소의 점검 상태를 초기화한다. 이후 재시작은 DB의 상태를 그대로 복구한다. `autoDeployTrigger: off`로 커밋 즉시 배포를 방지하고 준비 확인 후 운영자가 수동 배포한다.

## 2. 연결 및 인증

- [ ] 배포된 HTTPS 주소의 `/`, `/healthz`, `/api/version`이 정상 응답한다. 예상 Git 버전, 카드 해시, 성장 해시가 일치한다.
- [ ] 승인 대상 Git 체크아웃에서 `npm run online:smoke -- https://게임서버주소` 실행. 버전/AI/카탈로그/계정/보안 헤더/WebSocket을 확인하고 카드·성장 해시, `data/ai-release`의 호환 모델(없으면 기본값) 세대 및 가중치가 서버와 일치해야 `releaseMatched: true`가 된다. 로컬 학습 원본은 승인 모델로 취급하지 않는다. 이 기본 검사는 공개 서버의 사용자 데이터에 접근하거나 로그인하지 않는다.
- [ ] 테스트 계정 A를 직접 등록한다. 이메일 확인이 필요하면 수신 및 로그인 허용 여부를 확인한다. 복구 기능을 켰다면 복구 코드를 발송해 테스트 계정으로만 리허설한다.
- [ ] PC 브라우저와 갤럭시 S24의 서로 다른 브라우저 세션에서 동일한 계정 A로 로그인한다.
- [ ] `CARD_DUEL_SMOKE_EMAIL`, `CARD_DUEL_SMOKE_PASSWORD` 환경 변수에 이미 등록한 **테스트 계정**의 인증 정보를 잠시 설정하고 `npm run online:smoke -- https://게임서버주소 --account`를 실행한다. 두 개의 독립 세션에서 계정 진행 기록 및 성장 해시, 역할, 실시간 인증을 비교한다. 새 계정 등록이나 대전/XP/덱 수정은 하지 않는다. 점검용 두 세션만 로그아웃하며 기존 기기 세션은 유지한다. 종료 후 임시 환경 변수도 제거한다.
- [ ] 일반 계정은 개발자 상태 API와 개발자 시험에 들어갈 수 없다. 별도의 검증된 테스트 개발자 계정을 지정하고 동일한 시험에서 권한을 확인한다. `--account`의 `identityBound: true`로 잘못된 표시 계정의 기록 조회가 거절되는 것도 확인한다.
- [ ] 공개 가입을 열기 전에 호스팅 프록시 환경의 인증 요청 제한을 시험한다. 현 버전은 직접 연결 주소·이메일·전체 인증 요청 제한을 적용하며 임의 전달 IP 헤더는 신뢰하지 않는다. 실제 신뢰 가능한 프록시 경로와 헤더 위조 차단을 검증한 뒤에만 전달 IP를 사용할 수 있다. [Render 프록시 신뢰 안내](https://render.com/articles/how-to-proxy-analytics-through-your-own-domain) 참고.
- [ ] 개발자 계정에서 패치 준비 상태를 확인한 후 테스트용 신규 경기를 열기 위해 점검을 종료한다.

### 선택: 배포 API 자동 승인 시험

서버 저장소와 WebSocket의 실제 쓰기 경로를 검증하려면 **일반 유저로 등록·인증한 미사용 폐기 가능 계정 A/B 두 개**를 별도로 준비한다. 일반 유저의 실계정은 절대 사용하지 않는다. `CARD_DUEL_TEST_A_EMAIL`, `CARD_DUEL_TEST_A_PASSWORD`, `CARD_DUEL_TEST_B_EMAIL`, `CARD_DUEL_TEST_B_PASSWORD` 환경 변수에 임시 설정하고 승인 소스의 `npm run online:acceptance -- https://게임서버주소 --disposable-test-accounts`를 실행한다. 기존 진행·덱·전적·활성 경기나 개발자 권한이 있거나 점검 중이면 실패한다. 동일 버전 및 승인 해시도 사전 확인한다.

성공 시 계정 A의 덱 1개, 랭크 AI 1경기(퀘스트 1회·XP 정산), 계정 A/B의 PvP 기록 1경기가 **실제로 서버에 남는다**. 시작 전에 서로 다른 두 시험 계정의 쿠키/표시 계정을 섞은 기록 조회·덱 저장·대전 진입 요청을 거절하는지 확인하고, 성공 결과에 `identityBound: true`가 표시된다. 세 독립 시험 세션만 종료한다. 실패 중간에 저장 경기나 덱이 남을 수 있으므로 기존 시험 계정에 반복 실행하지 않는다. 시험용 데이터는 운영자의 계정 폐기 절차로만 정리한다. 환경 변수도 종료 후 제거한다. 이 도구는 물리 PC/폰 브라우저, 실제 이메일 수신, 별도의 서버 재배포 검증을 대체하지 않는다.

## 3. PC ↔ 모바일 계정 성장

- [ ] 같은 브라우저 두 탭에서 계정 A의 화면을 띄운 뒤 별도 시험 계정 B로 로그인한다. 이전 A 화면에서 덱 저장/다운로드/대전 진입을 시도하면 B의 진행 기록이 변하지 않고 계정 재확인 안내가 표시되는지 확인한다. 탭을 포커스하면 새 계정으로 갱신된다.

- [ ] PC에서 합법 덱을 이름과 함께 서버 저장 → 모바일에서 새로고침 없이 덱 표시 → 불러오기. 반대로 모바일에서도 같은 시험을 한다.
- [ ] 두 기기 각각 다른 이름으로 덱을 동시에 저장해 두 저장본 모두 남는지 확인한다. 같은 이름의 수정과 삭제가 충돌하는 경우 최신 저장본을 가져오며 편집 중인 덱은 유지되고 사용자가 다시 확인해야 한다.
- [ ] 계정 A의 시작 랭크(브론즈 5)와 XP, 초기 보유 카드 수가 두 기기에서 일치한다. 계정 B는 별도 진행 기록을 가진다.
- [ ] 보유 카드만 사용한 랭크 AI 대전 시작. 다른 기기 로비에 활성 경기/랭크/연결 상태가 표시되고 신규 경기 버튼이 차단된다.
- [ ] 진행 중 저장하고 나가기 또는 네트워크 연결 해제 → 다른 기기에서 이어하기 → 손패/전장·경기 상태 유지 확인.
- [ ] 퀘스트 직업으로 유효한 경기 완료 → 확정된 XP/퀘스트/해금 카드/승급 정보를 확인 → 두 기기 새로고침 및 로그아웃/재로그인 후 동일.
- [ ] 게임 초기의 항복은 XP를 얻지 않는다. 25개 랭크 및 9직업 퀘스트 순서, 다음 카드 XP 표시를 확인한다. 편집된 클라이언트 요청으로 임의 XP나 미해금 카드 사용은 서버가 거절해야 한다.
- [ ] 미해금 카드의 순차 획득 및 성장 추천 덱에 보유 카드만 포함됨을 확인한다. 실제 밸런스 수치는 검토 범위가 아니다.

## 4. 사람 대전과 개발자 권한

- [ ] 테스트 계정 B를 만들고 A와 B가 친구 코드 참가 및 자동 상대 찾기를 각각 시험한다.
- [ ] 게스트 및 같은 계정끼리의 계정 PvP 참가와 미해금 덱은 거절한다.
- [ ] PvP 종료 후 양 계정의 전적만 기록되고 랭크 AI XP는 동일하다. 연결 해제·복구 및 대전 종료를 함께 시험한다.
- [ ] 개발자 계정에서 랭크 1과 25 시험을 실행하고 다른 사용자는 접근할 수 없음을 확인한다. 개발자 시험에 XP/전적 보상이 없음을 확인한다.

## 5. 후속 패치 및 장애 복구

- [ ] 테스트 계정의 덱·XP·랭크·보유 카드·전적을 해당 계정 내 기록 다운로드로 확인한다(기록을 서버로 가져오는 기능은 아님).
- [ ] 계정 AI를 진행하다가 저장하고 시험 서버를 재시작한다. 동일한 카드 해시에서 복구가 되는지 확인한다.
- [ ] 점검 모드 켜기 → 신규 계정 경기/서버 덱 저장·삭제/비밀번호 변경·복구 완료 차단, 기존 경기 및 이미 접수한 변경 유지 → 모두 종료 및 정산. 개발자 운영 상태에서 계정 패치 준비 완료 확인. 로그인과 가입, 현재 기기 덱 편집은 가능하다.
- [ ] 현재 실행 중인 운영 버전의 Git 체크아웃에서 테스트 개발자 계정 환경 변수를 설정하고 `npm run online:smoke -- https://게임서버주소 --ready` 실행. `releaseMatched: true`, `patchReadiness.readyForPatch: true` 확인. 신규 배포 전 마지막 조회 시점의 상태이며 점검을 해제하거나 자동 배포하지 않는다. 새 버전 배포 후에는 새 소스에서 다시 확인한다. 실패하면 원인을 해결하고 재검사한다.
- [ ] 배포 전 DB 백업/복원 절차를 운영자와 검토한다. 실제 개인 데이터는 기존 소스 ZIP에 포함하지 않는다.
- [ ] 새 버전으로 빌드·배포한다. 새 서버는 DB에 저장된 점검 상태를 보존한 채 시작. 기존 인스턴스가 요청을 더 이상 처리하지 않는지 확인 후 점검을 종료한다.
- [ ] 새 버전과 성장 해시 일치, 기존 계정 진행 기록 보존, 새 브라우저의 업데이트 확인, 기존 카드 해금 영구 보존. 새 버전과 이전 버전 양쪽에서 `online:smoke` 및 배포 사전 검사를 각각 실행할 수 있다.
- [ ] 운영자는 이전 소스 버전 및 설정 백업을 이용한 롤백을 시험 서버에서 검증한다. 운영 DB를 이전 스냅숏으로 무조건 덮어쓰지 않는다.

## 공개 출시 판단

로컬 자동 시험은 앱 코드의 기능을 확인하지만 실제 HTTPS, 외부 가입, PostgreSQL 원장, 전자메일, 물리 기기, 네트워크 지연 및 클라우드 수용량을 보장하지 않는다. 위 검증을 모두 끝내기 전에는 개발 후보/테스트 서비스로만 표시한다. 카드 밸런스 및 AI 강도 검증, 공개 서비스의 운영 정책은 별도 과제로 유지한다.
